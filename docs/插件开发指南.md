# 插件与扩展开发指南

这篇指南回答三个问题：**业务能力实现哪个接口、项目需要什么依赖、写好的实现怎样在 Agent 中生效。**

下面先介绍如何给客服 Agent 添加商店说明，再扩展到订单工具、执行拦截和应用主动查询。
示例以文档中的代码片段展示。只想使用现成官方插件，可以直接阅读[能力包组合](#能力包组合)。

普通业务能力优先使用 `#[extension_point]` + `#[capability(...)]` + `CapabilityPack` 声明并自动装配；
需要工具描述、模型绑定或配置值时使用 `#[capability_factory]`。
`Plugin` 管理服务注册和资源生命周期；`CapabilityPack` 统一组合官方和业务插件、扩展实现及资源。

本页的 Rust Plugin 和声明式能力包编译进宿主，运行在宿主进程内。
宿主通过 Cargo 依赖、features 和代码依赖选择编译内容，再通过 AgentBuilder 选择启用内容。
官方默认插件和第三方 Rust 插件使用相同的原生装配链；未选中的声明式能力不执行工厂。

独立安装的扩展使用[动态能力包](动态能力包运行时设计.md)。清单声明 `backend`，
且选中了扩展实现、插件或页面时，运行时启动独立后端；官方发布的安装包也遵循这条规则。
未声明后端的静态包不启动能力包后端。来源验签不改变加载方式，
MCP stdio 与系统命令进程则由相应插件管理。

仓库中的具体实现按职责放在 `crates/plugin/<分类>`，Rust 能力包装配入口放在 `crates/capability`。
这些目录不承担官方身份认证或进程隔离判断；外部安装包由管理器保存和选择。
来源、交付方式、执行方式及默认能力见 [Crates 组织](../crates/README.md)。

## 基本概念

**提供系统上下文，先实现 `ContextContributor` 中的业务方法。**
普通业务实现再用 `#[capability(...)]` 标记，应用选择包后框架会在准备模型输入时调用它。
`ContextContributorPlugin::new(id, provider)` 仍可手工注册；它是兼容的注册封装，不会额外生成上下文业务逻辑。

| 概念 | 作用 | 示例 |
|---|---|---|
| 能力接口 | 定义一个业务扩展点，由框架在对应时机调用 | `ContextContributor` 提供系统或开发者指令 |
| 能力实现 | 保存业务配置，实现接口中的方法 | `ShopContext` 生成商店说明 |
| `CapabilityPack` | 统一分发、配置、版本选择和装配插件与扩展实现 | Shop、订单、审计及官方组合 |
| 注册封装 | 手工将一个能力实现接入 Plugin 安装流程 | `ContextContributorPlugin` 注册传入的 Provider |
| `Plugin` | 定义安装过程，可创建资源、解析依赖并注册多种能力 | `OrdersPlugin` 注册订单服务和查询工具 |

应用通过 `AgentBuilder` 的 `.capability_pack(...)`、`.plugin(...)` 或
`.plugin_factory(...)` 配置能力；`build().await` 才创建实例并安装插件。运行和关闭等操作统一由
Agent 实例完成。添加 Cargo 依赖只让宏声明可发现，**只有选中能力包或手工注册 Plugin 才会生效**。
Provider 本身不要求实现 `Plugin`。简单业务能力使用能力包；需要组织复杂安装过程时，再阅读
[什么时候需要自己实现 Plugin](#什么时候需要自己实现-plugin)。

```text
ShopContext + #[capability]    声明业务能力和包归属
    ↓ 应用选择
CapabilityPackBuilder          保存当前 Agent 配置和显式子包
    ↓ build().await
预校验 → factory → Plugin      创建、适配并安装上下文实现
    ↓
agent.run(request)             准备模型输入时调用 ShopContext::context
```

## 引入依赖

### 区分插件项目和应用项目

一个可复用插件通常放在 library crate 中；创建和运行 Agent 的应用放在 binary crate 中。
以一个商店客服业务项目 `shop-assistant` 为例，在同一个 Cargo workspace 中管理插件和应用：

```text
shop-assistant/                            业务项目
├─ Cargo.toml                             workspace 与公共依赖
├─ shop-plugin/                            你开发的插件库
│  ├─ Cargo.toml
│  └─ src/lib.rs
└─ shop-agent/                             使用插件的应用
   ├─ Cargo.toml
   └─ src/main.rs
```

框架作为外部 Cargo 依赖引入。业务项目只包含自己的插件和应用代码。

### 业务项目根目录的 Cargo.toml

根目录统一声明 workspace 成员和框架依赖，插件与应用继承这些依赖：

```toml
[workspace]
members = ["shop-plugin", "shop-agent"]
resolver = "2"

[workspace.dependencies]
eliteforge-agent-core = "0.1.0"
eliteforge-agent-framework = { version = "0.1.0", default-features = false }
eliteforge-agent-official-capability-pack = "0.1.0"
```

这里假设使用的 Cargo 源已提供上述 crate 的 `0.1.0` 版本，仅用于演示依赖声明，
不表示这些包已发布到 crates.io。接入时使用实际可用的版本和源；使用私有源时，
在 `.cargo/config.toml` 中配置源，并在对应依赖中添加 `registry`。

### 插件项目的 Cargo.toml

```toml
[package]
name = "shop-plugin"
version = "0.1.0"
edition = "2024"
publish = false

[dependencies]
eliteforge-agent-core = { workspace = true }
async-trait = "0.1"
serde_json = "1"
tokio-util = { version = "0.7", features = ["rt"] }
```

- `eliteforge-agent-core`：`capability`、`CapabilityPackBuilder`、`Plugin`、`PluginContext`、
  各种扩展接口及注册类型。插件作者的主要依赖。
- `async-trait`：用于示例中的异步接口实现。
- `serde_json`：订单工具的参数和 JSON Schema；只写商店指令插件时可以不引入。
- `tokio-util`：主动查询接口接收 `CancellationToken`；没有这类操作时可以不引入。

`shop-plugin` 的生产依赖不需要 Framework。它描述自己的能力，不创建 Agent。
如果插件需要数据库驱动、HTTP client 等实现依赖，在这个项目中另外声明。

### 应用项目的 Cargo.toml

```toml
[package]
name = "shop-agent"
version = "0.1.0"
edition = "2024"
publish = false

[dependencies]
shop-plugin = { path = "../shop-plugin" }
eliteforge-agent-framework = { workspace = true }
eliteforge-agent-official-capability-pack = { workspace = true }
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
```

`shop-plugin` 是应用自己的插件库，Framework 负责装配和执行，官方包提供模型、存储、问答、
AGUI、MCP 和遥测。`tokio` 提供异步运行时。

`workspace = true` 表示继承业务项目根目录声明的依赖。
`shop-plugin` 的 `path` 相对应用的 `Cargo.toml`，指向同一业务项目中的插件库。

Cargo 包名里的 `-` 在 Rust 的 `use` 路径里写成 `_`，例如 `shop-plugin` 对应 `shop_plugin`。

## 用能力包提供系统上下文

目标：让模型收到“你是星河商店的客服，请使用中文回答”。业务 crate 声明能力，应用不再逐项调用
`ContextContributorPlugin::new(...)`。

将下面实现放到 `shop-plugin/src/lib.rs`：

~~~rust
use async_trait::async_trait;
use eliteforge_agent_core::{
    capability, AgentError, ContextContributor, ContextSourceKind, ContextInput, ContextBlock, Message, RunContext,
};

pub struct ShopConfig {
    pub name: String,
}

pub struct ShopContext {
    name: String,
}

impl ShopContext {
    pub fn from_config(config: &ShopConfig) -> Self {
        Self {
            name: config.name.clone(),
        }
    }
}

#[capability(
    pack = "shop",
    config = ShopConfig,
    factory = ShopContext::from_config
)]
#[async_trait]
impl ContextContributor for ShopContext {
    fn kind(&self) -> ContextSourceKind { ContextSourceKind::Instruction }
    fn block_id(&self) -> &str { "shop.instructions" }
    async fn contribute(&self, input: &ContextInput<'_>) -> Result<ContextBlock, AgentError> {

        let messages: Result<Vec<Message>, AgentError> = async {
        Ok(vec![Message::system(format!(
            "你是{}的客服，请使用中文回答。",
            self.name
        ))])
     }.await;
        messages.map(|messages| ContextBlock::instructions(self.block_id(), messages))
    }
}
~~~

应用选择包并提供当前 Agent 的配置：

~~~rust
use eliteforge_agent_core::CapabilityPackBuilder;
use eliteforge_agent_framework::AgentBuilder;
use shop_plugin::ShopConfig;

let agent = AgentBuilder::new()
    .capability_pack(CapabilityPackBuilder::new(
        "shop",
        ShopConfig {
            name: "星河商店".into(),
        },
    ))
    .build()
    .await?;
~~~

上例省略了 `id` 和 `instance`；同一类型实现多个 trait 时按包和实际 Rust 类型身份复用该
实例，支持跨模块实现和类型别名。需要跨能力排序、命名或创建多份同类型对象时，再显式写 `depends_on`、`id` 和
`instance`。配置型 factory 必须是 `fn(&ShopConfig) -> ShopContext`；同步 factory 之外的
连接建立或服务解析应留在普通 Plugin。

包必须显式选择。即使应用也链接了 Payment crate，只要没有
`.capability_pack(CapabilityPackBuilder::new("payment", ...))`，Payment 的 factory 不会执行。
子包使用 `.include(...)` 加入。完整字段、共享实例、Skills 成员、依赖和生命周期见
[能力包与自动装配](能力包与统一装配.md)。

## 手工注册 Provider（兼容入口）

目标：让模型收到“你是星河商店的客服，请使用中文回答”这条系统指令。
下面先写 Provider，再把它配置给 Agent。这个场景不需要自己实现 `Plugin`。

### 第一步：实现 ContextContributor

将下面代码放在业务项目的 `shop-plugin/src/lib.rs` 中：

```rust
use async_trait::async_trait;
use eliteforge_agent_core::{AgentError, ContextContributor, ContextSourceKind, ContextInput, ContextBlock, Message, RunContext};

pub struct ShopContext {
    name: String,
}

impl ShopContext {
    pub fn new(name: impl Into<String>) -> Self {
        Self { name: name.into() }
    }
}

#[async_trait]
impl ContextContributor for ShopContext {
    fn kind(&self) -> ContextSourceKind { ContextSourceKind::Instruction }
    fn block_id(&self) -> &str { "shop.instructions" }
    async fn contribute(&self, input: &ContextInput<'_>) -> Result<ContextBlock, AgentError> {

        let messages: Result<Vec<Message>, AgentError> = async {
        Ok(vec![Message::system(format!(
            "你是{}的客服，请使用中文回答。",
            self.name
        ))])
     }.await;
        messages.map(|messages| ContextBlock::instructions(self.block_id(), messages))
    }
}
```

`ShopContext` 保存商店名称，`context` 返回模型指令。业务逻辑到这里就写完了。
内置执行器准备每轮模型输入时，会调用已配置的 Provider；这里的方法也可以使用传入的 `RunContext`。
系统和开发者指令、检索数据统一使用 `ContextContributor`；指令来源声明 `kind() = Instruction` 并组合进内置指令块，检索来源保留默认 `Data` 并配置独立布局和配额。

如果指令就是一段固定文字，可以直接使用已经实现 `ContextContributor` 的 `FixedInstructions`：

```rust
use eliteforge_agent_core::FixedInstructions;

let provider = FixedInstructions::new("shop.instructions", "你是星河商店的客服，请使用中文回答。");
```

### 第二步：把 Provider 配置给 Agent

当前 `AgentBuilder::plugin` 接收实现了 `Plugin` 的对象，使用 `ContextContributorPlugin` 将 Provider 接入这个入口：

```rust
use eliteforge_agent_core::ContextContributorPlugin;
use eliteforge_agent_framework::AgentBuilder;
use eliteforge_agent_official_capability_pack::EliteForgeOfficialCapabilityPack;
use shop_plugin::ShopContext;

let agent = AgentBuilder::new()
    .capability_pack(EliteForgeOfficialCapabilityPack::new("agent.sqlite", "agent-artifacts"))
    .plugin(ContextContributorPlugin::new(
        "shop.context",
        ShopContext::new("星河商店"),
    ))
    .build().await?;
```

`ShopContext` 生成指令，`ContextContributorPlugin` 负责安装注册；换成 `FixedInstructions` 时也是同样的注册方式。
`shop.context` 是这项安装配置在当前 Agent 内的 ID，用于重复检查、依赖排序和错误定位。

片段位于异步函数中，模型配置见[默认模型装配](模型插件设计.md#默认装配)。
应用使用 `agent.run(...)` 发起运行，结束使用后调用 `agent.close().await` 关闭资源，错误路径也应执行关闭逻辑。

多个应用需要按配置自动装配同一组业务能力时，使用上面的 `CapabilityPack` 声明。
若只是复用已经创建好的 Provider，再使用兼容的[能力包组合](#能力包组合)。

### ContextContributorPlugin 具体做了什么

`ContextContributorPlugin` 是框架提供的 `struct`，已经实现了 `Plugin`。它只有以下注册职责：

| 时机 | 行为 |
|---|---|
| `ContextContributorPlugin::new(id, provider)` | 保存安装 ID，用 `Arc` 持有传入的 Provider |
| `build()` 调用它的 `install` | 将 Provider 注册为一个 `ContextContributorService` |
| Agent 准备模型输入 | 框架调用注册的 Provider，由 Provider 返回指令 |

`ContextContributorPlugin` 不生成指令、不检索知识，也不负责上下文裁剪或记忆存储。
这些能力分别由 Provider 或对应的其他扩展接口实现。
安装时，注册封装执行的核心代码是：

```rust
context.contribute(ContextContributorService(self.implementation.clone()))
```

这一行解释了封装的内部行为；使用者只需传入 Provider，无需重复这段注册代码。
工具来源、事件监听和中间件分别有 `ToolProviderPlugin`、`EventPlugin`、`RunMiddlewarePlugin` 等同类封装。

## 什么时候需要自己实现 Plugin

当安装过程需要解析其他服务、异步建立连接、注册多种相关能力或登记关闭回调时，再实现 `Plugin`。
给业务 Provider 传入名称、规则等普通配置，优先使用上一节的能力包；已有对象的手工注册仍可使用
`ContextContributorPlugin` 等封装。

例如，一个订单插件可以在 `install` 中创建订单服务，同时注册模型查询工具和应用主动查询入口。
完整注册过程见[订单工具](#提供模型可调用的工具)，依赖及资源规则见[依赖与生命周期](#依赖与生命周期)。

| 你要做什么 | 需要编写什么 |
|---|---|
| 添加按配置创建的业务上下文 | `ContextContributor` impl + `#[capability]`；应用选择 `CapabilityPack` |
| 手工添加已有系统上下文 | `ContextContributor` 实现；使用 `ContextContributorPlugin` 注册 |
| 添加一段固定指令 | 使用 `FixedInstructions` 和 `ContextContributorPlugin` |
| 复用一组已经创建好的 Provider | 用注册封装组成兼容的 `CapabilityPack`，应用只安装包 |
| 安装时创建并管理业务资源 | `Plugin::install`，并登记适用的关闭回调 |
| 一次安装工具、上下文等多种能力 | 自定义 `Plugin`，或将独立注册配置组成包 |

## 按场景选择扩展点

先根据**谁发起调用、你要改变哪一步**选择接口。一个插件可以同时注册多个扩展点。

| 业务场景 | 首先关注的扩展点 | 下一步 |
|---|---|---|
| 添加角色、系统规则或开发者指令 | `ContextContributor` | 已在[入门示例](#用能力包提供系统上下文)中实现 |
| 每次调用模型前检索知识、记忆或业务数据 | `ContextContributor` + `ContextLayout` | [加入检索结果](#加入检索结果) |
| 让模型决定什么时候查订单、调接口 | `Tool`，必要时再实现 `ToolProvider` | [提供模型可调用的工具](#提供模型可调用的工具) |
| 工具执行前拒绝操作或要求审批 | `ToolPolicy` | [权限与人工交互](#权限与人工交互) |
| 模型主动向用户提问 | `HumanInteractionPlugin` 或返回交互请求的 `Tool` | [权限与人工交互](#权限与人工交互) |
| 统计、拦截或修改一次执行的结果 | 对应层级的 `Middleware` | [拦截执行](#拦截执行) |
| 只关心一次运行开始和结束 | `RunLifecycleHook` | [接收通知与输出](#接收通知与输出) |
| 收集文本增量、工具事件、错误等 | `EventSink` | [接收通知与输出](#接收通知与输出) |
| 为应用提供自己的输出流类型 | `RunOutputFactory` + `EventSink` | [接收通知与输出](#接收通知与输出) |
| 应用主动查询插件能力，参数由应用决定 | `AgentOperation` | [让应用主动调用插件能力](#让应用主动调用插件能力) |
| 接入新的模型协议或多模态服务 | `ChatModel` 或相应的模型接口 | [接入模型](#接入模型) |
| 更换会话、执行状态或记忆存储 | 对应的存储接口 | [替换存储](#替换存储) |
| 增加固定业务步骤、分支或并行任务 | `WorkflowNode` + DAG 配置 | [扩展工作流](#扩展工作流) |
| 整体改变 Agent 的决策执行方式 | `AgentLoop` | [扩展工作流](#扩展工作流) |

### 提供模型可调用的工具

以“查询订单”为例，分成三部分：

- `ToolDescriptor`：告诉模型工具叫什么、有什么作用、参数是什么。`id` 是框架内部身份，`call_name` 是模型调用名。
- `Tool::call`：模型给出参数后，框架实际执行的业务代码。
- `ToolProvider`：为当前运行提供工具列表。固定列表直接用 `StaticToolProvider`；根据用户权限或当前任务动态提供工具时，再自行实现 `lease`。

下面用内存中的固定订单 `A100 → 已发货` 演示 `lookup_order` 的调用链。
接真实业务时，把目录查询替换为自己的数据库或接口调用。

```text
模型返回 lookup_order(order_id="A100")
    ↓
框架校验参数、权限、取消和预算
    ↓
ToolMiddleware → LookupOrderTool::call
    ↓
ToolOutput("订单 A100：已发货")
    ↓
结果加入消息 → 模型继续回答
```

下面代码定义订单数据、查询工具及其注册过程，可放在插件库的 `orders` 模块中：

```rust
use async_trait::async_trait;
use eliteforge_agent_core::*;
use serde_json::{Value, json};
use std::{collections::BTreeMap, sync::Arc};
use tokio_util::sync::CancellationToken;

struct OrderCatalog {
    orders: BTreeMap<String, String>,
}

pub struct OrderCatalogService(Arc<OrderCatalog>);

struct LookupOrderTool {
    catalog: Arc<OrderCatalog>,
}

#[async_trait]
impl Tool for LookupOrderTool {
    async fn call(&self, arguments: Value, context: &RunContext) -> Result<ToolOutput, ToolError> {
        if context.is_cancelled() {
            return Err(ToolError::Failed("订单查询已取消".into()));
        }
        let id = arguments["order_id"]
            .as_str()
            .ok_or_else(|| ToolError::Failed("order_id 必须是字符串".into()))?;
        match self.catalog.orders.get(id) {
            Some(status) => Ok(ToolOutput::text(format!("订单 {id}：{status}"))),
            None => Ok(ToolOutput::error(format!("没有找到订单 {id}"))),
        }
    }
}

pub struct OrdersPlugin;

#[async_trait]
impl Plugin for OrdersPlugin {
    fn id(&self) -> &str {
        "shop.orders"
    }

    async fn install(&self, context: &mut PluginContext<'_>) -> Result<(), PluginError> {
        let catalog = Arc::new(OrderCatalog {
            orders: BTreeMap::from([("A100".into(), "已发货".into())]),
        });
        // 主动查询操作与模型工具共享同一份订单数据。
        context.provide(OrderCatalogService(catalog.clone()))?;
        let descriptor = ToolDescriptor::new(
            "shop.orders.lookup",
            "lookup_order",
            "根据订单号查询订单状态",
            json!({
                "type": "object",
                "properties": {"order_id": {"type": "string"}},
                "required": ["order_id"],
                "additionalProperties": false
            }),
        );
        context.contribute(ToolProviderService(Arc::new(StaticToolProvider::new(
            vec![ToolBinding::new(descriptor, LookupOrderTool { catalog })],
        ))))
    }
}
```

在插件库入口用 `pub mod orders;` 导出模块后，应用安装插件：

```rust
use shop_plugin::orders::OrdersPlugin;

let builder = builder.plugin(OrdersPlugin);
```

`OrdersPlugin::install` 内通过 `contribute(ToolProviderService(...))` 注册工具来源。
固定工具也可直接配置 `ToolProviderPlugin::new(id, StaticToolProvider::new(bindings))`。

工具返回的业务失败可使用 `ToolOutput::error`；无法可靠完成调用时返回 `ToolError`。
工具派发后丢失结果属于“不确定是否已执行”，不要自行把这种情况当作普通失败反复重试。
MCP 服务器已提供工具时，直接配置官方包的 `.mcp(...)`，无需再实现一层 `Tool`。

### 加入检索结果

**系统规则、文档、记忆和订单数据使用同一个 `ContextContributor` 接口，由 `DefaultContextAssembler` 读取。**
`kind() = Instruction` 的来源返回受信任的 System/Developer 指令并组合进内置指令块；默认 `Data` 来源只能返回 User 数据消息。内置历史适配器保留完整对话和工具协议。
`ContextContributor::contribute` 则返回一个有 ID 的 `ContextBlock`，例如 `ContextBlock::data("shop.knowledge", content)`。

开发步骤：

1. 实现 `block_id()`，为来源指定稳定 ID。
2. 实现 `contribute(&ContextInput)`，根据当前输入、模型、阶段、历史和预算查询数据。
3. 使用 `ContextContributorPlugin::new(id, implementation)` 注册。
4. Data 来源同时用 `ContextLayoutPlugin` 配置块顺序和 token 配额；布局必须包含内置指令、历史和每个 Data 来源。Instruction 来源组合到内置指令块，不添加独立布局槽。

固定数据也能用同一条装配链，下面的片段展示必须一起配置的两个插件：

```rust
use eliteforge_agent_core::*;

let builder = builder
    .plugin(ContextContributorPlugin::new(
        "shop.knowledge",
        FixedContextContributor(ContextBlock::data("shop.knowledge", "退货期限为 7 天。")),
    ))
    .plugin(ContextLayoutPlugin(ContextLayout(vec![
        ContextBlockConfig::new(INSTRUCTIONS_BLOCK, BlockBudget::tokens(1000)),
        ContextBlockConfig::new("shop.knowledge", BlockBudget::tokens(1000)),
        ContextBlockConfig::new(HISTORY_BLOCK, BlockBudget::tokens(4000)),
    ])));
```

检索数据超长时关注 `ContextReducer`；需要重新分配各块预算时关注 `ContextBudgetPolicy`。
只有要整体接管组装流程时才实现 `ContextAssembler`；这时应把来源、布局、预算和裁剪规则一起配置在自己的组装器内部。
可运行的检索、摘要压缩和附件示例见[上下文窗口](上下文与会话设计.md)。

### 拦截执行

先选拦截范围，再实现 `intercept`。例如统计一次运行耗时，使用 `RunMiddleware`：

```rust
use async_trait::async_trait;
use eliteforge_agent_core::{
    AgentError, RunContext, RunMiddleware, RunNext, RunRequest, RunResult,
};
use std::time::Instant;

pub struct TimingMiddleware;

#[async_trait]
impl RunMiddleware for TimingMiddleware {
    async fn intercept(
        &self,
        _: &RunRequest,
        _: &RunContext,
        next: RunNext<'_>,
    ) -> Result<RunResult, AgentError> {
        let started = Instant::now();
        let result = next.run().await;
        eprintln!(
            "run finished: success={}, elapsed={:?}",
            result.is_ok(),
            started.elapsed()
        );
        result
    }
}
```

注册时使用现成的适配器：

```rust
use eliteforge_agent_core::RunMiddlewarePlugin;
use shop_plugin::timing::TimingMiddleware;

let builder = builder.plugin(RunMiddlewarePlugin::new("shop.timing", TimingMiddleware));
```

| 想包围哪一段执行 | 接口 | 继续执行的方法 |
|---|---|---|
| 一次 `agent.run/start` 对应的执行 | `RunMiddleware` | `next.run().await` |
| 一次 DAG 节点执行 | `WorkflowNodeMiddleware` | `next.run(input, context).await` |
| 一次 Chat 模型调用 | `ModelMiddleware` | `next.run(request, context).await` |
| 一次工具调用 | `ToolMiddleware` | `next.run().await` |

`ModelMiddleware` 用于 Chat 调用；Embedding、图片等独立模型操作不经过这条 Chat 中间件链。
`next` 只能消费一次。先注册的中间件在外层，实际顺序还受插件依赖排序影响：

```text
A 前置 → B 前置 → 业务执行 → B 后置 → A 后置
```

只统计开始/结束而不改变执行时，也可以用 `RunLifecycleHook`。
上面的耗时示例只记录正常返回路径；取消或超时可能丢弃 future，资源关闭必须使用下文的生命周期机制。
返回值、错误和取消语义详见[Middleware 与 Hook](插件中间件与生命周期.md)。

### 权限与人工交互

工具是否允许执行、是否需要审批，用 `ToolPolicy::evaluate` 返回 `Allow`、`Deny` 或 `RequireApproval`，
通过 `ToolPolicyPlugin::new(id, policy)` 注册。不要用生命周期 Hook 返回错误来代替权限策略。

模型需要主动向用户提问时，官方包已经提供 `HumanInteractionPlugin`，模型可以调用 `ask_user`。
自定义交互工具也可返回 `ToolOutput::request_input(InteractionRequest)`。

```text
工具请求提问 / 策略要求审批
    ↓
运行返回 AwaitingInput，交互记录被持久化
    ↓
应用展示问题 → agent.answer(session, id, answer)
    ↓
得到恢复请求 → agent.run(resume_request)
```

应用用户身份及外部业务授权仍由上层应用处理。使用自定义 `AgentLoop` 时，它还必须声明并实现工具策略执行能力。
完整提问、审批与跨进程恢复代码见[用户交互](用户交互与审批.md)。

### 接收通知与输出

| 你需要什么 | 使用什么 | 注册与触发 |
|---|---|---|
| 一次运行开始/结束通知 | `RunLifecycleHook` | `RunLifecycleHookPlugin`；回调 `on_started/on_finished` |
| 文本增量、工具活动等运行事件 | `EventSink` | `EventPlugin`；接收 `on_event` 或发布时的 `on_published` |
| 应用订阅框架原始事件 | Agent 自带入口 | `agent.events(&mut handle)`，无需自定义插件 |
| 给前端发送 AGUI | 官方 `AgUiPlugin` | 包已安装；用 `agent.start_with_output::<AgUiStream>` |
| 自定义协议输出 | `RunOutputFactory` + `EventSink` | 注册 `RunOutputService` 与 `EventService` |

`RunLifecycleHook` 只接收通知，不能修改运行结果，失败会被隔离。
`EventSink::on_event` 通过有界观测队列消费，慢消费者可能丢事件；`on_published` 在发布路径同步调用，不能阻塞。
这些接口不承担可靠业务消息投递或资源关闭保证。

自定义输出时，在同步的 `prepare` 中创建每次执行独立的通道，把接收端写入 `RunOutputs`，
把发送端放入该次运行的 `Extensions`；再由 `EventSink` 转换并发送事件。
`prepare` 在首个运行事件前执行，同一接收端只能通过 `agent.output::<T>` 取一次。
完整实现可参考[AGUI 插件](../crates/plugin/protocol/eliteforge-agent-official-plugin-agui/src/lib.rs)，前端接法见[AGUI 文档](AG-UI事件协议.md)。

### 让应用主动调用插件能力

“用户点击查询订单按钮”由应用决定参数，可以使用 `agent.execute(FindOrder { ... })`。
它直接调用已安装的服务，不需要先让模型生成工具调用。

沿用上面的 `OrdersPlugin` 注册的 `OrderCatalogService`，请求类型通过 `AgentOperation::Service` 声明要使用的服务：

```rust
// 应用主动调用的请求；参数由应用传入。
pub struct FindOrder {
    pub order_id: String,
}

#[async_trait]
impl AgentOperation for FindOrder {
    type Service = OrderCatalogService;
    type Output = Option<String>;

    async fn execute(
        self,
        service: Arc<Self::Service>,
        cancellation: CancellationToken,
    ) -> Result<Self::Output, AgentError> {
        if cancellation.is_cancelled() {
            return Err(AgentError::Cancelled);
        }
        Ok(service.0.orders.get(&self.order_id).cloned())
    }
}
```

把这段实现放在订单插件所在模块中，与工具共享同一份订单数据。
应用只操作 Agent：

```rust
use shop_plugin::orders::FindOrder;

let status = agent.execute(FindOrder { order_id: "A100".into() }).await?;
```

默认要求服务唯一；多个候选服务时，实现 `select` 按请求中的名字或其他明确规则选择。
Agent 负责准入、取消和关闭顺序。该调用不会经过模型工具的 `ToolPolicy`/`ToolMiddleware` 链；
需要业务鉴权时，由上层应用或该操作实现负责。
取消 token 的生命周期覆盖本次调用，返回、调用方丢弃 future 或 Agent 关闭时都会取消。

### 接入模型

已有协议先配置 Genai；只改变选择哪个模型时，关注 `ModelRoutingPlugin` 或 `ModelSelectionStrategy`。
只有需要实现协议适配时，才实现 `ChatModel::generate`，再用 `ChatModelPlugin` 或 `ModelConnectionPlugin` 注册。

Embedding、重排序、图片、视频、语音和实时会话各有独立接口和服务注册类型。
不能因为实现了 `ChatModel` 就获得这些能力。注册方法与适用接口见[模型扩展点](插件扩展点参考.md#模型)，
协议、路由、环境变量及完整配置见[模型插件](模型插件设计.md)。

### 替换存储

先明确需要替换的数据：

| 要存什么 | 实现哪些接口 | 注册适配器 |
|---|---|---|
| 对话消息 | `ConversationStore` + `ConversationSession` | `ConversationStorePlugin` |
| 执行 checkpoint、journal 和租约 | `StateStore` | `StateStorePlugin` |
| 提问、审批和答案 | `InteractionStore` | `InteractionStorePlugin` |
| 跨对话长期记忆 | `LongTermMemory` | `LongTermMemoryPlugin` |
| 历史摘要 | `SummaryStore`（Context Contracts crate） | 自定义插件注册 `SummaryStoreService` |
| 附件与工具大结果 | `ArtifactStore`（Context Contracts crate） | 自定义插件注册 `ArtifactStoreService` |
| 动态模型目录元数据 | `ModelCatalogStore` | `ModelCatalogStorePlugin` |

每种角色在同一个 Agent 内只有一个实现。官方包的本地存储插件已经注册了上面全部角色。
换数据库或附件目录时，修改包的 `.storage(...)`。
**要改用另一套存储实现，应单独装配插件或建立自己的能力包**：当前官方包的 `storage` 参数只接受 `LocalStoragePlugin`。

例如，会话存储可换成你自己的实现，执行状态和交互存储继续使用其他已实现的插件；
不要再同时安装覆盖这些角色的整套本地存储插件。

会话存储还要实现消息一致性、版本检查和租约释放，执行存储还要实现原子状态迁移；
接口详细职责见[存储参考](插件扩展点参考.md#存储)与[执行契约](执行契约.md)。

### 扩展工作流

已有 DAG 调度能表达流程时，实现一个 `WorkflowNode`：声明 `kind()`、配置 schema、
`validate` 和 `execute`，通过 `WorkflowNodePlugin::new(id, node)` 注册，再在 DAG 定义中引用该 `kind`。
节点只有被流程引用并调度时才会执行；只注册插件不会自动增加流程步骤。

需要替换整个决策循环时，实现 `AgentLoop`，使用 `AgentLoopPlugin::new(loop)` 注册。
同时声明模型、状态、交互、恢复、工具策略等需求，框架在构建时校验。
这是高级扩展；循环需要自己遵守取消、持久化和工具执行契约。
完整 DAG 示例与恢复规则见[DAG 工作流](DAG工作流.md)。

## 能力包

`CapabilityPack` 是业务能力的自动装配入口。业务 crate 在 trait `impl` 上使用
`#[capability(...)]`；应用通过 `.capability_pack(...)` 选择包和配置。描述会跨已链接 crate
收集，但只有根包和 `.include(...)` 明确加入的子包会实例化。

~~~rust
use eliteforge_agent_core::CapabilityPackBuilder;

let pack = CapabilityPackBuilder::new("shop", shop_config)
    .include(CapabilityPackBuilder::new("shop.audit", audit_config));

let agent = AgentBuilder::new()
    .capability_pack(pack)
    .build()
    .await?;
~~~

`build()` 先预校验能力 ID、依赖、环和共享实例声明，再按稳定拓扑顺序调用同步 factory。
同一 `instance` 的多接口声明共享业务对象；不同 Agent 各自创建和关闭实例。未选包的 factory
不会运行。factory 始终同步且只读取包配置；连接、后台任务和服务绑定放进返回插件的
`install`，完整服务集合在 `ready` 中读取。

能力包统一负责业务发现、配置、组合和版本选择；
普通 Plugin 仍解决复杂安装和资源生命周期。完整宏字段和错误边界见
[能力包与自动装配](能力包与统一装配.md)。

框架已经提供可选的文件系统工具能力包，以及独立的通用系统命令能力包；它们不携带平台、空间或
业务资源语义。目录范围、可选程序限制、跨平台调用方式和安全边界见
[能力包说明](能力包与统一装配.md)。

## 能力包组合

能力包通过 `plugins()` 提供直接成员，通过 `included_packs()` 提供子包。构建器同时支持普通插件和可重建工厂；元数据收集阶段不连接数据库、不启动后端。

```rust
use eliteforge_agent_core::{CapabilityPackBuilder, ContextContributorPlugin, FixedInstructions};

let context_pack = CapabilityPackBuilder::new("shop.context-pack", ())
    .plugin(ContextContributorPlugin::new("shop.rules", FixedInstructions::new("shop.instructions", "以订单工具返回的结果为准。")));
// AgentBuilder::new().capability_pack(context_pack).build().await
```

直接提供的插件在重配时保留原实例和配置。需要切换配置的插件改用 `ConfiguredPluginFactory`；工厂在依赖图通过预检之后执行。

### 官方能力包

`EliteForgeOfficialCapabilityPack` 默认装配这些官方能力：

| 插件 | 默认行为 | 修改配置 |
|---|---|---|
| Genai | 安装时读取 `MODEL` 等模型环境配置 | `.model(plugin)`；支持自定义模型插件 |
| 本地存储 | SQLite 保存结构化数据，文件系统保存附件正文；数据库与受保护的附件目录都由宿主指定 | `.storage(LocalStoragePlugin)` |
| 用户问答 | 注册 `ask_user` 工具 | `.human_interaction(false)` 可关闭 |
| Agent 协作工具 | 注册 `agent_spawn` 和 `thread_create/send/answer/wait/read/list/close` | `.agent_tools(false)` 可关闭；默认 runtime 见[Agent 协作](Agent协作.md) |
| Skills | 发现系统级与当前目录的 Agent Skills；元数据进入上下文，模型按需加载详情与资源 | `.skills(SkillsPlugin)` 替换配置；`.without_skills()` 可关闭 |
| AGUI | 每次运行准备 AGUI 输出 | `.agui(plugin)` 修改配置；`.without_agui()` 可关闭 |

`model`、`storage`、`human`、`agents`、`skills`、`agui`、`mcp`、`telemetry` 模块从官方包重新导出相应插件类型。
具体配置例子见[快速上手](快速上手.md#使用官方能力包)；模型环境变量见[模型插件](模型插件设计.md#默认装配)。
`.without_model()` 只移除包内模型；Framework 的自动补充开关仍由 `.default_models(false)` 控制。

### 组合多种能力

能力包可以通过 `CapabilityPackBuilder::include(child)` 嵌套，并通过 `.plugin(...)` 或 `.plugin_factory(...)` 添加成员。插件、扩展实现和子包统一参与依赖排序。官方组合由[实现](../crates/capability/eliteforge-agent-official-capability-pack/src/lib.rs)维护。

## 构建时如何收集能力

框架不会扫描任意对象实现了哪些 trait。它收集两种明确来源：宏登记并被选中能力包激活的描述，
以及手工安装的 Plugin 注册的服务。

~~~text
#[capability] trait impl                    ContextContributorPlugin / 自定义 Plugin
             │                                          │
             ▼                                          ▼
静态 CapabilityDescriptor                     install 时注册服务
             │                                          │
capability_pack + include 筛选                 plugin / capability_pack 配置
             │                                          │
预校验 → factory → 适配 Plugin ────────────────┘
                         │
                         ▼
                 PluginContainer 安装
                         │
                         ▼
all::<ContextContributorService>() → 按来源 kind 装配；Instruction 组合到内置指令源，Data 进入显式布局
~~~

`AgentBuilder::build` 使用 `all::<ContextContributorService>()` 取得上下文列表；工具来源、事件监听和
其他多贡献接口也按各自服务类型汇总。能力描述的处理顺序按依赖和稳定 ID 决定；手工 Plugin 的
安装顺序仍由其依赖图决定。实际消息还会经过上下文布局和预算处理。

| 操作 | 是否会加入 Agent 的上下文来源 |
|---|---|
| 仅在依赖 crate 中写 `impl ContextContributor` | 不会 |
| 标记 `#[capability]`，但不选择对应包 | 不会，factory 也不运行 |
| 标记 `#[capability]` 并选择对应 `CapabilityPack` | 会 |
| 把 Provider 交给 `ContextContributorPlugin`，再直接或通过 `CapabilityPack` 安装 | 会 |
| 在自定义 Plugin 中调用 `contribute(ContextContributorService(...))` | 会 |
| 仅把业务对象作为自身类型注册 | 不会，业务对象类型与 `ContextContributorService` 是不同注册键 |

业务侧不需要直接操作发现库。能力包的选择、实例化、共享和错误边界见
[能力包与自动装配](能力包与统一装配.md)。

## 多个插件与配置替换

有两个不同的身份需要区分：插件通过字符串 `id()` 标识，服务通过具体 Rust 类型标识。

| 写法 | 含义 | 多个实现时的行为 |
|---|---|---|
| `provide(T)` | 注册一个唯一角色 | 同类型第二次注册报 `DuplicateService` |
| `contribute(T)` | 向某种能力的实现列表追加一项 | 按安装及注册顺序保留多个实现 |
| 同一个 T 混用两种方式 | 注册语义冲突 | 报 `ServiceKindConflict` |
| 重复插件 ID | 同一 Agent 内身份冲突 | 安装前报 `DuplicatePluginId` |

多个贡献怎么用，由对应扩展点决定：事件插件都接收事件，中间件形成调用链，工具来源合并，
模型按连接和模型选择规则解析，自定义操作通过 `select` 选服务。
工具身份、模型绑定、上下文块 ID、工作流节点 kind、运行输出类型还各有进一步的唯一性校验。

框架不按插件 Rust 类型自动覆盖旧实例，也没有“后注册的插件自动成为默认实现”的规则。
同类型插件能否多实例，取决于 ID、注册的服务角色和该领域的约束。

官方包已经包含本地存储；在包外再次安装 `LocalStoragePlugin` 会重复。
正确的配置替换发生在包展开之前：

```rust
let pack = EliteForgeOfficialCapabilityPack::new("agent.sqlite", "agent-artifacts")
    .storage(LocalStoragePlugin::new("other.sqlite", "other-artifacts"));
```

这里最终只安装一个存储插件。多个独立 Agent 可以分别使用自己的存储配置。

## 依赖与生命周期

### 解析另一个插件的服务

需要另一个插件先安装时，在 `dependencies()` 返回它的**插件 ID**。
例如，一个依赖订单目录的插件声明：

```rust
fn dependencies(&self) -> Vec<String> {
    vec!["shop.orders".into()]
}
```

然后在自己的 `install` 中解析所需服务：

```rust
let catalog = context.services()
    .get::<shop_plugin::orders::OrderCatalogService>()
    .ok_or_else(|| PluginError::message("缺少订单目录服务"))?;
```

`dependencies` 控制安装顺序；`get<T>`/`all<T>` 按服务类型解析，两者不能互相代替。
解析后把引用传给你创建的业务实现。运行期间应用仍调用 Agent，不从容器取出内部服务自行调度。

如果你希望支持多种供应商插件，不要把依赖 ID 写死为某个厂商；将依赖 ID 做成插件配置，
并始终对所需服务类型进行检查。缺失依赖或依赖环会在任何插件安装前失败。

能力声明使用 `depends_on = ["..."]` 表达同样的安装前后关系。它可以依赖已选能力或应用显式
配置的普通 Plugin，但不会自动选择另一个能力包；框架保留的内部 ID 也不能作为能力依赖。
静态能力 ID、缺失依赖和依赖环都会在调用 capability factory 前失败；预检包含应用传入的
普通插件依赖边。自动创建的 Plugin 自身的动态 `dependencies()` 只能在构造后读取，
需要提前校验的依赖应写入宏的 `depends_on`。

### 资源在哪创建、在哪关闭

| 时机 | 该做什么 |
|---|---|
| `#[capability]` | 只登记静态描述；不创建对象、连接或后台任务 |
| `CapabilityPackBuilder::new / include` | 保存当前 Agent 配置和显式子包；不调用 factory |
| 能力包解析 | 先预校验，再按稳定依赖顺序调用同步 factory 并适配为 Plugin |
| `new`、各配置方法 | 保存普通 Plugin 配置，校验同步参数 |
| `CapabilityPack::plugins` | 组合插件配置 |
| `Plugin::install` | 创建连接或后台任务，立即注册清理回调，再注册服务或扩展 |
| `Plugin::ready` | 全部安装完成后读取完整服务/扩展集合、绑定消费者和校验配置；不能再注册服务 |
| 扩展点回调 | 执行业务，遵守传入的取消信号和限额 |
| `agent.close().await` | 停止接收新操作，取消并等待在途操作，调用插件关闭回调 |
| 安装失败、取消或 Drop | 回滚已持有的资源，执行适用的清理回调 |

拿到资源后，先注册清理，再继续可能失败或被取消的异步操作。
`on_shutdown` 用于异步关闭；`on_cleanup` 用于 Drop/取消时的同步兜底。
需要同时提供二者的资源，应让清理可重复调用，例如“先发取消信号，再等待后台任务退出”。
回调按注册的逆序处理。若关闭被超时打断，同步兜底仍要能释放或停止资源。

插件内部任务用插件生命周期管理；一次运行内的工具连接或临时会话分别使用 `ToolLease`、
`ConversationSession` 等对应作用域。`RunLifecycleHook::on_finished` 是通知，不是必达的资源释放点。
真实连接和清理注册可参考[MCP 插件](../crates/plugin/tool/eliteforge-agent-official-plugin-tools-mcp/src/lib.rs)
与[本地存储插件](../crates/plugin/storage/eliteforge-agent-official-plugin-storage-local/src/lib.rs)。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| 只引入依赖，能力没有生效 | 还没有选择 `.capability_pack(...)`，或没有调用 `.plugin(...)` / `.capability_pack(...)` 注册 |
| 实现了接口，框架仍没调用 | 能力包路径核对 trait impl 是否标记 `#[capability]` 且包已选中；第三方接口核对是否有 `#[extension_point]`，手工路径核对服务或扩展是否已注册 |
| 未选的业务包仍创建了资源 | factory、连接或后台任务写进了静态注册/构造路径；factory 只接收配置，资源初始化移到 Plugin 安装期 |
| 加上第二个存储插件就构建失败 | 重复插件 ID 或唯一存储角色冲突；修改现有配置，或重新组合存储插件 |
| 明明有插件，`get<T>()` 仍返回空 | 具体注册类型不匹配，或该类型使用了 `contribute`，应在插件内部用 `all<T>()` |
| 自定义上下文来源构建失败 | Data 类型的 `ContextContributor` 需要完整的 `ContextLayout`，包括每个数据来源的 ID 和配额 |
| 想在 Hook 里拒绝运行 | 使用 `RunMiddleware`；拒绝工具或要求审批使用 `ToolPolicy` |
| 想给 Agent 加一个自定义查询方法 | 定义 `AgentOperation` 请求，通过 `agent.execute(request)` 调用 |
| 插件 install 失败后资源泄漏 | 资源取得后没有立即注册清理；补上异步关闭和必要的同步兜底 |

更完整的接口、注册类型、调用时机和数量约束见[扩展点参考](插件扩展点参考.md)。
